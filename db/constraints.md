# Обоснование ограничений

Схема `trofimov_food`. Скрипты лежат в `db/schema` и выполняются в таком порядке: `create_types.sql`, `create_tables.sql`, `add_constraints.sql`, `create_triggers.sql`, `generator.sql`, `functions.sql`, `views.sql`, `grants.sql`.

Таблицы создаются без ключей, все PK, FK, UNIQUE и CHECK добавлены отдельно через `alter table ... add constraint` в `add_constraints.sql`. Имена ограничений начинаются с `pk_`, `fk_`, `uq_`, `ck_`, по имени видно, что это и на какой таблице.

Таблица заказов названа `"order"` в кавычках, как в `erd.md` (BR-13.1). Переименовывать не стал, чтобы имя совпадало с контрактом.

## Ловушки

### Ловушка 1: `payment` - неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

```
1. pay_method pay_kind              - каким способом платили в этой попытке (BR-8.2, BR-8.6)
2. amount numeric(14,2)             - сумма попытки (BR-8.2)
3. transaction_ref varchar(40)      - номер транзакции от платёжного провайдера (BR-8.2, BR-8.3)
4. transaction_timestamp timestamp  - когда прошла транзакция (BR-8.2)
5. status attempt_state             - успех, ошибка или в обработке (BR-8.2)

transaction_ref, а не transaction_id: это строка провайдера, а не наш ключ.
Все столбцы *_id в схеме - uuid (BR-11.1), строковый *_id выбивался бы из правила.
Номеров карт и других данных карт нет (BR-1.7, BR-8.5).
```

**Где хранится тип оплаты - `payment` или `order`** (BR-8.6):

```
В payment. По BR-8.6 у одного заказа могут быть попытки разными способами,
значит способ - свойство попытки. В "order" только итоговый pay_status (BR-7.8).

Остальные правила по оплате:
1. Сумма попытки = total_amount заказа (BR-8.4). Это проверяет триггер tg_payment_amount
   (функция check_payment) перед вставкой и изменением попытки. Если сумму не передали,
   триггер подставляет сумму заказа сам. Обычным check это не сделать: сумма заказа
   лежит в другой таблице.
2. Чтобы сумма не разошлась с другой стороны, триггер tg_order_sums не даёт поменять
   order_amount у заказа, по которому уже есть попытки оплаты.
3. Успешная попытка у заказа одна (BR-8.1): частичный уникальный индекс
   uq_payment_success on payment (order_id) where status = 'успех'.
4. pay_status заказа (BR-8.7) пересчитывает триггер tg_payment_pay_status
   (функция refresh_pay_status) после вставки, изменения и удаления попытки:
   есть 'успех' -> 'оплачен'; иначе есть 'в_обработке' -> 'ожидает';
   иначе есть 'ошибка' -> 'ошибка'; попыток нет -> 'ожидает'.
```

### Ловушка 2: `order.address_id` - принадлежность клиенту (BR-7.4)

**Как обеспечено, что адрес доставки принадлежит клиенту:**

```
Составной внешний ключ:

alter table "order" add constraint fk_order_client_address
	foreign key (client_id, address_id) references client_address (client_id, address_id);

Пара (client_id, address_id) - первичный ключ client_address, поэтому на неё можно ссылаться.
Заказ на адрес, которого нет у этого клиента, не вставится.
Плюс к этому связь клиента с адресом нельзя удалить, пока по ней есть заказы,
так история заказов не ломается (BR-3.5).

Простые FK fk_order_client и fk_order_address тоже оставил, они повторяют ссылки из erd.md.
```

### Ловушка 3: `order_structure` - один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

```
Триггер tg_order_structure_position (функция check_position), before insert or update
на order_structure. Он сравнивает restaurant_id блюда и restaurant_id заказа и при
несовпадении падает с ошибкой "блюдо ... и заказ ... из разных ресторанов".

Составным FK тут не обойтись: restaurant_id нет в order_structure, а добавлять его
туда значило бы дублировать данные заказа.
Одно блюдо дважды в заказе не встретится, потому что PK order_structure - (order_id, product_id) (BR-7.16).
```

### Ловушка 4: `review` - полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

```
Оставил полиморфизм, как в erd.md: entity_type + entity_id. На entity_id нет FK,
потому что он ссылается то на блюдо, то на ресторан, то на заказ. Проверки такие:

1. 'заказ': check ck_review_order_target (entity_type != 'заказ' or entity_id = order_id).
   Отзыв на заказ может быть только на тот заказ, к которому он привязан, а сам order_id
   проверяется обычным FK.
2. 'ресторан': триггер tg_review_object (функция review_object_check) проверяет,
   что заказ сделан именно в этом ресторане.
3. 'блюдо': тот же триггер проверяет, что блюдо есть в составе заказа.
   Так выполняется BR-9.2: отзыв только на то, что клиент заказал.
4. Клиент отзыва - владелец заказа: составной FK fk_review_order_client
   (order_id, client_id) -> "order" (order_id, client_id). Для него на "order"
   есть unique (order_id, client_id).
5. Не больше одного отзыва на объект в одном заказе (BR-9.5): unique (order_id, entity_type, entity_id).

Почему не три отдельные таблицы отзывов: в erd.md отзыв одна сущность, а rating_change
(FOOD-105) и бэкенд работают с entity_type. Три таблицы дали бы три одинаковых
набора столбцов и три триггера.
```

## DEFAULT и GENERATED

| Таблица | Столбец | Что | Обоснование |
|---|---|---|---|
| все таблицы | `*_id` (кроме ссылок) | `default exts.uuid_generate_v4()` | BR-11.1: uuid выдаёт сервер |
| `courier` | `coefficient` | `default 0.1` | BR-6.5: стартовый коэффициент |
| `courier` | `status` | `default 'свободен'` | новый курьер ещё без заказа |
| `courier` | `hire_date` | `default current_date` | обычно курьера заводят в день найма |
| `restaurant` | `status` | `default 'активен'` | подключённый ресторан сразу работает |
| `product` | `status` | `default 'доступно'` | новое блюдо можно заказывать |
| `"order"` | `order_timestamp` | `default localtimestamp` | BR-7.1, BR-11.2: время создания по часам сервера, без часового пояса |
| `"order"` | `status` | `default 'создан'` | первый статус заказа (BR-7.7) |
| `"order"` | `pay_status` | `default 'ожидает'` | попыток ещё нет (BR-8.7) |
| `payment` | `transaction_timestamp` | `default localtimestamp` | BR-11.2 |
| `payment` | `status` | `default 'в_обработке'` | попытка только началась |
| `review` | `review_timestamp` | `default localtimestamp` | BR-9.3, BR-11.2 |

`commission` и `total_amount` - обычные столбцы, не `generated`. Их заполняет триггер `tg_order_sums` (функция `order_sums`) перед вставкой и при изменении любой из трёх сумм: комиссия = `round(order_amount * 0.1, 2)`, итог = `order_amount + commission`. Приложению достаточно передать стоимость блюд. Почему не `generated`: в этом же триггере стоит запрет менять сумму заказа после появления оплат (BR-8.4), а вычисление и запрет логично держать в одном месте. Чтобы данные не разошлись, даже если триггер отключат, оставлен `check` `ck_order_sums`.

Длины и точность (BR-11.6): деньги `numeric(14,2)`, количество `numeric(7,2)` (бывает дробным, BR-7.15), рейтинги `numeric(5,2)`, коэффициент `numeric(3,1)`, оценка в отзыве `numeric(1)`. Типы строк взяты из `erd.md`: пароль `varchar(32)` (MD5 всегда 32 символа), телефоны клиента и курьера `char(12)`, то есть `+7` и 10 цифр, номер всегда одной длины.

## Нормализация (3НФ)

```
1НФ: значения атомарные. Адрес разбит на улицу, дом и квартиру (BR-3.1), у заказа
несколько блюд, поэтому позиции вынесены в order_structure, а не списком в заказе.
ФИО курьера одним полем, как в BR-6.1 и erd.md.

2НФ: составные ключи только у client_address, order_structure и courier_pay.
quantity зависит от всей пары (заказ, блюдо), amount и coefficient_used - от курьера
и месяца вместе. Частичных зависимостей нет.

3НФ: неключевые столбцы зависят только от ключа. Спорные места:
1. commission и total_amount считаются из order_amount. Хранятся, потому что они есть
   в erd.md и нужны отчётам. Расхождение невозможно: их пишет триггер tg_order_sums
   и проверяет ck_order_sums.
2. order_amount не пересчитывается из позиций: цены блюд меняются, а сумма заказа
   фиксируется в момент заказа.
3. product.rating и restaurant.rating - средние по отзывам. Это осознанная денормализация:
   рейтинг показывается в каждом списке блюд и ресторанов, считать его каждый раз
   по review дорого. Актуальность держит триггер rating_change (FOOD-105).
4. order.pay_status - итог по попыткам оплаты, его держит refresh_pay_status.
5. review.client_id можно найти через заказ, но он есть в erd.md. Расхождение
   исключает составной FK fk_review_order_client.
6. courier.coefficient - не копия courier_pay: это коэффициент, который действует сейчас
   (BR-6.4), а в courier_pay лежат уже применённые.
7. review.entity_type и entity_id зависят только от review_id, полиморфизм 3НФ не ломает.
```

## Заметки по процедурам

1. **insert_test_data(value)** заполняет таблицы циклами. id создаются заранее через `exts.uuid_generate_v4()` и складываются в массивы, дальше случайные клиенты, рестораны и курьеры берутся по индексу массива, без `order by random()` в цикле. Блюда создаются сразу за своим рестораном (по 5), адреса клиента сразу за клиентом (по 4), у каждого третьего клиента есть ещё один адрес, общий с соседним клиентом (BR-2.4).
   - Для заказа сначала выбирается курьер, а дата заказа берётся внутри периода его работы, поэтому уволенный курьер не получит заказ после увольнения.
   - Каждое из 5 блюд ресторана попадает в заказ с вероятностью 0.4, одно выбирается обязательно. Блюда не повторяются (BR-7.16). Если сумма с комиссией меньше 1000 ₽, растёт количество первой позиции.
   - Статус попытки оплаты: у заказов в работе и доставленных `'успех'`, у созданных и отменённых случайный. `pay_status` генератор не пишет, его ставит триггер по попытке (BR-8.7).
   - Отзыв по одному на заказ, объект выбирается одним индексом: тот же номер берётся в `enum_range(null::review_target)` и в массиве `[блюдо, ресторан, заказ]`.
2. **Повторные вызовы.** Логины, телефоны, названия категорий и номера транзакций идут со счётчика от текущего количества строк и проверяются на занятость. Заказы нового вызова ссылаются только на новых клиентов, рестораны и курьеров, поэтому старые выплаты не устаревают.
3. **courier_pay в генераторе** считается рекурсивным CTE по месяцам для новых курьеров: в первом месяце коэффициент 0.1 (BR-6.5), коэффициент месяца n берётся по доставкам месяца n-1 (BR-10.2), после увольнения не меняется (BR-10.6). Сумма = коэффициент × комиссии доставленных заказов месяца. В `courier.coefficient` записывается коэффициент на следующий месяц. Месяц определяется по `order_timestamp`.
4. **Генератор не вызывает другие процедуры** схемы. Триггеры на вставку срабатывают сами, поэтому рейтинги блюд и ресторанов после генерации уже равны среднему по отзывам, а `pay_status` совпадает с попыткой оплаты.
5. **courier_salary()** работает одним запросом с CTE: в `s` считаются доставки и комиссии курьеров за текущий месяц, дальше обновляются существующие записи `courier_pay`, вставляются недостающие и пересчитывается коэффициент работающим курьерам. При повторном запуске в том же месяце берётся уже записанный `coefficient_used`, поэтому сумма не меняется и дубликатов нет (BR-10.3).
6. **get_statistic()** читает `"order"` один раз (CTE `sold`). Лучшее блюдо и лучший клиент ищутся через `max` по «весу»: к количеству блюда прибавляется `random() / 1000`, к числу заказов клиента `random() / 2`. Добавка меньше шага значения (0.01 у количества и 1 у числа заказов), поэтому порядок не меняется, а при равенстве побеждает случайный. Без оконных функций и без `lateral`.
7. **how_much_money** строит месяцы рекурсивным CTE по номеру месяца `год * 12 + месяц - 1`, от первого до последнего месяца с доставленными заказами. Месяцы без заказов попадают в отчёт с нулями (BR-11.9), прошлый месяц берётся через `lag`.
8. **erase_test_data()** одной командой `truncate ... cascade` от корневых таблиц `address`, `client`, `courier`, `product_category`: остальные восемь очищаются по внешним ключам. Типы, функции и триггеры не затрагиваются.
