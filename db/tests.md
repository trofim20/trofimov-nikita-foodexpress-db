# Протокол для самопроверки

Все проверки ниже сделаны на базе, восстановленной из `db/foodexpress_trofimov.backup`. До восстановления роли `inspector` в кластере не было, её создал `grants.sql`. Запросы выполнялись под `inspector` (вход `psql -U inspector`), кроме тех, где написано иначе.

## Как развернуть

1. В базе должна быть схема `exts` с расширением `uuid-ossp`. В окружении курса она уже есть. В пустой базе её создают первые строки `db/schema/create_types.sql` (`create schema if not exists exts` и `create extension if not exists "uuid-ossp" with schema exts`).
2. `pg_restore -U postgres -d <база> db/foodexpress_trofimov.backup`
3. `psql -U postgres -d <база> -f db/schema/grants.sql`

Бэкап сделан командой `pg_dump -Fc -n trofimov_food -x` (PostgreSQL 16). В нём только схема `trofimov_food` с данными одного вызова `insert_test_data(10)`. Прав в бэкапе нет (`-x`), их выдаёт `grants.sql`, поэтому восстановление не зависит от того, есть ли уже роль `inspector`. `grants.sql` можно запускать повторно.

Без бэкапа схема собирается из `db/schema` в порядке: `create_types.sql`, `create_tables.sql`, `add_constraints.sql`, `create_triggers.sql`, `generator.sql`, `functions.sql`, `views.sql`, `grants.sql`.

## E. Функции и процедуры

- **E.1. `add_product`, успешный вызов.** Параметры названы и упорядочены как в шаблоне: `p_restaurant_id`, `p_product_category_id`, `p_name`, `p_price`, `p_rating`, `p_status`, `p_description`, `p_photo_url` (по умолчанию `null`, его можно не передавать). Вызов из шаблона дословно PostgreSQL не выполняет (`cannot use subquery in CALL argument`), это ограничение `call`, а не процедуры. Поэтому id взяты в переменные:

  ```sql
  do $$
  declare
  	v_rest uuid = (select restaurant_id from restaurant limit 1);
  	v_cat uuid = (select product_category_id from product_category limit 1);
  begin
  	call add_product(p_restaurant_id => v_rest, p_product_category_id => v_cat, p_name => 'Тестовое блюдо',
  		p_price => 250, p_rating => 4.5, p_status => 'доступно', p_description => 'Описание');
  end $$;
  ```

  Ожидается: `after = before + 1`. Факт: 550 → 551. **OK**
- **E.2. `add_product` с ошибками.** Ожидается: внятная ошибка. Факт:
  - несуществующий ресторан: `add_product: ресторан 00000000-0000-0000-0000-000000000000 не найден`;
  - несуществующая категория: `add_product: категория 00000000-0000-0000-0000-000000000000 не найдена`;
  - цена -250: `add_product: цена не может быть отрицательной, передано -250`;
  - рейтинг 7: `add_product: рейтинг должен быть от 0 до 5, передано 7`.

  **OK**
- **E.3. `rating_change` при вставке.** Запрос из шаблона берёт случайный заказ и случайного клиента, такой отзыв схема не пропускает: блюдо должно быть в заказе (BR-9.2), клиент должен быть владельцем заказа. Поэтому взята пара заказ-блюдо из `order_structure` и клиент этого заказа:

  ```sql
  create temp table tp as
  select os.product_id, os.order_id, o.client_id
  from order_structure os
  join "order" o on o.order_id = os.order_id
  where not exists (select 1 from review r where r.order_id = os.order_id and r.entity_type = 'блюдо' and r.entity_id = os.product_id)
  limit 1;

  insert into review (client_id, review_timestamp, entity_id, entity_type, order_id, description, rating)
  select client_id, localtimestamp, product_id, 'блюдо', order_id, 'Тестовый отзыв', 5 from tp;
  ```

  Ожидается: рейтинг пересчитан. Факт: у блюда был один отзыв и рейтинг `2.00`, после отзыва с оценкой 5 стало `3.50`, это совпадает с `round(avg(rating), 2)`. Проверка из бэклога FOOD-105 на одном блюде: отзывы 3, 4, 5 → `4.00`; удалили тройку → `4.50`; удалили все → `NULL`. **OK**
- **E.4. `rating_change` при удалении.** Ожидается: если других отзывов нет, `NULL`, иначе пересчитан. Факт: отзыв из E.3 удалён, у блюда остался один отзыв, рейтинг снова `2.00`. Случай без отзывов проверен выше: после удаления всех отзывов `NULL`. **OK**
- **E.5. `get_statistic()`.** Ожидается: пять колонок с нужными именами, строка на ресторан, `best_user` - логин. Факт: 110 строк на 110 ресторанов, `total_amount < avg_amount` нет ни разу, `best_user` вида `user22`. У ресторана без доставленных заказов суммы 0, а блюдо и клиент `NULL`. При равенстве выбор случайный: отдельно на 200 ресторанах функция вызвана 30 раз, лучший клиент менялся у 173 ресторанов, лучшее блюдо у 32, при этом каждый раз ровно одна строка на ресторан. **OK**
- **E.6. `courier_salary()`.** Ожидается: запись за текущий месяц, новый коэффициент работающим, уволенным без изменений. Факт: записей за 11.2026 было 110 (генератор уже создал текущий месяц), осталось 110, суммы пересчитаны по их `coefficient_used`. Коэффициенты на данных генератора 0.1, потому что ни у кого нет 150 доставок в месяц. Отдельная проверка в транзакции с откатом: курьеру добавлено 160 доставок в текущем месяце → `coefficient = 0.2`, `coefficient_used = 0.1`, сумма 1639.50; уволенному с коэффициентом 0.3 → остался 0.3. Если записи за месяц нет, она вставляется с текущим `courier.coefficient` (10 из 10 строк). **OK**

## Дополнительно: что схема не пропускает

Каждая команда выполнялась под `inspector` на сгенерированных данных. Все ошибки ожидаемые.

| Что пробовал | Результат |
|---|---|
| заказ на адрес, которого нет у клиента | `fk_order_client_address` |
| блюдо другого ресторана в состав заказа | триггер: «блюдо ... и заказ ... из разных ресторанов» |
| отзыв на блюдо, которого нет в заказе | триггер: «в заказе ... нет блюда ...» |
| отзыв на ресторан, где заказ не делали | триггер: «заказ ... сделан не в ресторане ...» |
| отзыв на чужой заказ (`entity_type = 'заказ'`) | `ck_review_order_target` |
| отзыв от клиента, который не делал заказ | `fk_review_order_client` |
| вторая успешная оплата заказа | `uq_payment_success` |
| оплата на сумму больше суммы заказа на 1 ₽ | триггер: «сумма попытки ... не совпадает с суммой заказа ...» |
| заказ на 550 ₽ | `ck_order_minimum` |
| изменить `order_amount` у заказа с оплатой | триггер: «по заказу ... уже есть оплата, сумму менять нельзя» |
| уволить курьера без даты увольнения | `ck_courier_dismissed` |
| удалить связь клиент-адрес, по которой есть заказ | `fk_order_client_address` |
| `insert_test_data(0)` | «value должно быть положительным, получено 0» |

Что схема исправляет сама (проверено в транзакциях с откатом):

- заказ с неправильной комиссией (1000 и 50) сохраняется с `commission = 100.00`, `total_amount = 1100.00`, их считает триггер;
- оплата без суммы получает сумму заказа;
- `pay_status`: все попытки удалены → `'ожидает'`, добавлена ошибочная → `'ошибка'`, добавлена успешная → `'оплачен'`.
